# PriceWatch - бизнес-правила MVP

## 1. Главное правило соответствия исходному заданию
Для каждой новой подтвержденной цены PriceWatch сравнивает ее с ПРЕДЫДУЩЕЙ подтвержденной ценой того же Offer.

Если снижение строго больше 10% (или больше пользовательского effective threshold, default 10%), отправляется Telegram-уведомление.

Формула:

```text
drop_percent = (previous_price - new_price) / previous_price * 100
```

При default threshold:
- 100 -> 90 = ровно 10%: уведомление НЕ требуется, потому что в задании указано `> 10%`;
- 100 -> 89 = 11%: уведомление требуется.

Предыдущая цена берется из последней принятой записи `price_history` до записи новой цены.

Ранее обсуждавшаяся `reference_price` для накопительного падения не входит в обязательный MVP и не должна подменять это правило. Ее можно добавить позже как отдельную дополнительную функцию.

## 2. Первичное добавление Offer
Ручное добавление через Telegram и CSV-import обязаны использовать одну core business logic.

В Telegram новый Product не записывается до явного подтверждения. Предварительная проверка URL может предложить надёжный `source_title`; пользователь вправе заменить его. Результат этой единственной предварительной проверки переиспользуется при финальной атомарной записи, поэтому подтверждение не вызывает второй одинаковый HTTP-запрос. Перед записью service повторно проверяет duplicate и ownership в SQLite-транзакции.

Валидный и разрешенный URL можно сохранить, даже если текущую цену при первой проверке получить не удалось.

### Первая проверка успешна
- создать/persist Offer;
- установить `current_price_minor` в первую принятую цену;
- записать `PriceHistory`;
- записать `CheckAttempt`;
- status -> `ACTIVE`;
- уведомление о снижении не отправлять, так как предыдущей цены еще нет.

### Первая проверка неуспешна/неоднозначна
Например `BLOCKED`, `AMBIGUOUS`, временная network error.

- сохранить Offer, если URL валиден и разрешен;
- `current_price_minor = NULL`;
- status -> `PENDING`;
- записать `CheckAttempt`;
- scheduler продолжает проверки в следующие дни.

При ручном добавлении сообщить пользователю, что товар добавлен, но текущую цену пока определить не удалось.

Первый последующий SUCCESS становится первой baseline-записью истории и не вызывает price-drop alert.

## 3. Обычная успешная проверка
До обновления состояния:
1. получить последнюю подтвержденную цену из `price_history`;
2. получить новую надежно извлеченную цену;
3. проверить валюту;
4. проверить аномалию относительно последней подтвержденной цены;
5. если цена не аномальна - принять ее;
6. сравнить новую цену с предыдущей для правила >10%;
7. записать новую цену в `price_history`;
8. обновить `offers.current_price_minor` и timestamps;
9. при необходимости отправить Telegram alert.

Каждая принятая успешная ежедневная проверка записывается в историю, даже если цена не изменилась.

## 4. Аномальная цена - дополнительная защитная функция
Порог MVP: абсолютное изменение >= 50% относительно последней подтвержденной `current_price_minor`.

Аномалия проверяется ДО принятия новой цены.

Если обнаружена аномалия:
- не обновлять `current_price_minor`;
- не писать цену в подтвержденную `price_history`;
- status -> `SUSPICIOUS`;
- сохранить `pending_price_minor`, `pending_price_detected_at`, связь с `CheckAttempt`;
- в `check_attempts.detected_price_minor` сохранить найденное значение;
- уведомить пользователя один раз и предложить действия:
  - открыть товар;
  - `CONFIRMED` - цена верна;
  - `REJECTED` - цена неверна;
  - изменить ссылку.

### CONFIRMED
- принять pending price;
- записать ее в `price_history` с временем фактического обнаружения;
- обновить `current_price_minor`;
- очистить pending-поля;
- status -> `ACTIVE`;
- не отправлять второе обычное price-drop уведомление за то же изменение, потому что пользователь уже получил anomaly notification.

### REJECTED
- confirmed current price не менять;
- зафиксировать решение в `CheckAttempt`;
- очистить/закрыть pending anomaly;
- продолжить мониторинг URL.

### Повтор той же pending anomaly
Пока решение пользователя ожидается, не отправлять одинаковое anomaly-уведомление ежедневно. Для MVP точное равенство `pending_price_minor` достаточно для определения того же значения; более сложный tolerance можно добавить позже.

Если новая проверка возвращает обычную надёжную цену, открытая pending anomaly теряет актуальность: pending-поля очищаются, новая цена принимается обычным путём и Offer возвращается в ACTIVE. Ошибка проверки при открытой anomaly, напротив, только записывается в CheckAttempt и не закрывает pending anomaly.

## 5. Повторные ошибки проверки
Не уведомлять пользователя о каждом временном сбое.

Для Offer, который ранее имел успешную цену:
- 1-я последовательная ошибка: `consecutive_errors = 1`, без уведомления;
- 2-я: `2`, без уведомления;
- 3-я: `3`, status -> `ERROR`, отправить одно уведомление, `error_notified = true`;
- дальнейшие ошибки не повторяют уведомление;
- первый последующий SUCCESS сбрасывает `consecutive_errors = 0`, `error_notified = false`, status -> `ACTIVE`.

Отдельное уведомление «мониторинг восстановлен» в MVP не требуется.

Offer, у которого еще никогда не было подтвержденной цены, остается `PENDING`; сообщение после трех ошибок должно ясно говорить, что первоначальную цену пока определить не удалось.

## 6. Валюта
Конвертация валют не входит в MVP.

Если валюта существующего Offer неожиданно изменилась, новую цену не принимать автоматически. Зафиксировать неуспешную/подозрительную проверку и сохранить последнюю подтвержденную цену.

Offers одного Product с разными валютами можно мониторить независимо, но нельзя объявлять «лучшую цену» простым числовым сравнением без конвертации.

## 7. CSV
- import и export обязательны;
- import использует `ProductService`;
- ошибка одной строки не откатывает остальные;
- duplicate URL пропускается и отражается в результате;
- BLOCKED/AMBIGUOUS URL может быть сохранен как PENDING Offer;
- CSV не должен иметь отдельные бизнес-правила, отличающиеся от ручного добавления.

## 8. robots.txt и публичные данные
Перед scraping учитывать `robots.txt`. Если доступ для выбранного URL запрещен, не обходить ограничение и зафиксировать `ROBOTS_DENIED`.

Не использовать CAPTCHA bypass, stealth, proxy rotation и другие способы обхода защиты.
